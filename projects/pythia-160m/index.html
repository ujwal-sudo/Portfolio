Pythia-160M

Research · In Progress

A Python-specialized code language model built from scratch

PyTorch Custom tokenizer RoPE · GQA · SwiGLU NTP + FIM

01 · Overview

Why train a model from scratch?

Pythia-160M is an ongoing exploration into training a small, Python-focused language model end to end. The goal isn't to compete with frontier models on scale; it's to understand every layer of the training stack from first principles.

When you call an API or fine-tune an existing checkpoint, the hardest engineering decisions have already been made for you. Building the tokenizer, implementing the attention heads, balancing the loss function, and curating the dataset forces you to confront the real failure modes of machine learning.

02 · Architecture

Modern transformer design choices

The architecture adopts modern design improvements developed across LLaMA, Mistral, and DeepSeek: rotary embeddings, grouped-query attention, SwiGLU non-linearities, and pre-RMSNorm.

03 · Objective

Dual Objective: Next-Token & Fill-In-The-Middle

Code models have a dual requirement: generating new code sequentially (left to right), and completing missing code inside an existing function or class (infilling).

Pythia uses a 50/50 training mixture between standard autoregressive causal language modeling and Fill-In-The-Middle (FIM):

// 1. Standard Next-Token Prediction (50% of tokens):

loss_ntp = cross_entropy(logits[:, :-1], targets[:, 1:])

// 2. Fill-In-The-Middle Formulation (50% of tokens):

transformed_sequence = [PRE] + prefix_tokens + [SUF] + suffix_tokens + [MID] + middle_tokens

// Model learns to predict middle_tokens conditioning on both prefix and suffix.

04 · Data Pipeline

Curating quality at small scale

At ~160M parameters, data quality matters significantly more than raw token volume. A small model easily memorizes noise, syntax errors, and low-quality boilerplate. The pipeline enforces 6 strict quality stages:

Stage 01

Provenance & Licensing

Permissively licensed Python repositories with complete git commit history.

Stage 02

Syntax Validation

All files parsed through Python AST; invalid syntax is filtered out immediately.

Stage 03

Exact & Near Deduplication

MinHash and line-level matching to purge repetitive boilerplate and copies.

Stage 04

Quality Heuristics

Filtering out auto-generated files, minified code, and test mock dumps.

Stage 05

BPE Tokenizer Training

Custom Byte-Pair Encoding preserving indentation and common Python keywords.

Stage 06

Token Packing & Shuffling

Packed 2048-token context buffers separated by EOS tokens.

05 · Constraints

Engineering within consumer hardware

Training on consumer hardware (single 24GB GPU) introduces real physical boundaries. To maximize throughput and avoid Out-Of-Memory exceptions:

  • Mixed precision: bfloat16 mixed precision to reduce memory footprint by 50% without loss scaling instability.
  • Gradient accumulation: Effective batch size of 512 achieved across smaller mini-batch steps.
  • Flash Attention 2: Subquadratic memory scaling during self-attention computation.
  • Activation checkpointing: Selective recomputation during backward pass for deep layers.

06 · Decisions & Trade-offs

Architectural rationale

Why GQA over MHA? Grouped-Query Attention with 2 KV heads reduces KV cache memory consumption during decoding by 6× while matching multi-head attention quality.

Why SwiGLU over GeLU? Although SwiGLU requires 3 weight matrices per feed-forward block instead of 2, it consistently shows lower perplexity per token on code tokens.
